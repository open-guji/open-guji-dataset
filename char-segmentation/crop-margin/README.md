# crop-margin —— s3 裁边残留空白纸边

## 这个分片量什么

s3 把页面裁到「版框外缘」，正常情况下裁完之后图像四边应该几乎不留
空白（干净页实测残留 0~25px）。但边框磨损重的页，`content_bounds`
的外框线检测会彻底找不到线，退化成「没找到就当图像边缘是边框」——
那一侧完全不裁，残留一大片扫描空白纸边。

来源：2026-08-27 用户提出「先裁后增强」的顺序实验（针对
`char_clustering_design.md` 里「浓墨粘连」截断专题），查证顺序本身
没错，但顺藤查出这个上游裁剪失手的问题。

## 为什么不需要人工标注

残留是图像里客观可数的东西——裁剪之后从图像边缘向内数，墨密度
（`< 128` 阈值下的暗像素占比）连续低于 0.5% 的区间有多长：

```
top    = 第一行「有墨」之前的行数
bottom = 最后一行「有墨」之后的行数
left / right 同理（按列）
```

超过 `flag_threshold_px`（50px，干净页实测噪声 0~25px，留 2 倍余量）
即记一页残留严重。金标只记「当前每一页残留多少」，回归口径：

- 干净页（<50px）**不许**变脏；
- 已经很脏的页**不许**变得更脏。

## 已知局限 / 一次修复尝试的负结果（2026-08-28）

**这个缺陷是真的，但已经试过一次修复，全书重建后是净负分，已撤销。**

修法是给 `_find_h_frame` 加一层墨密度兜底（边缘检测退化时改用
「行墨密度从空白转非空白」的第一个持续过阈值点当边界）。单页/9 页
样本验证极干净：90/90 全修好、0 新退步。**但铺到全书 394 页重建后
跑 open-guji-cv 的 12 闸回归**：`truncation`/`seam`/`jiazhu_tail`
（丢字 2 个）/`left_cut`/`char_drop` 全部失败，`frame_strip` 部分
样本字身墨掉了 31%，`recrop` 通过率从 32/40 掉到 21/40。

根因：s3 裁剪边界一变，图像内容的绝对像素坐标全部跟着变——下游一大
批闸（框渣剥离、侧边界行剥离、夹注段端归类、recrop、instances 自检
……）都是**对着旧的（偏松的）裁剪结果标定的绝对像素判据**，93 页的
裁剪边界一动，这批判据在这些页上集体错位，代价比修复本身救回的
truncation/seam 改善大得多。详细记录见
`open-guji-cv/.claude/doc/pipeline_handbook.md` §12。

**这不代表这个数据集没用**——缺陷本身、量法本身都是对的（90/90 单页
验证证明检测算法是对的），错的是「直接整册重建像素几何」这个修复
策略。留着这份金标，下次再有人想修，至少不用重新发现一遍缺陷，也
不用重新踩一遍「全书重建绝对像素判据集体错位」这个坑。

## 用法

```
PYTHONPATH=. python scripts/eval_crop_margin.py <dataset>/char-segmentation --intermediate-dir <s3_crop 中间产物目录>
PYTHONPATH=. python scripts/eval_crop_margin.py <dataset>/char-segmentation --intermediate-dir <...> --update
```

`--intermediate-dir` 指向含 `vol01/s3_crop`、`vol02/s3_crop`（或已重建
产物根目录 `vol01/*.png` 等）的目录——`preprocess --keep-intermediate`
的输出。
