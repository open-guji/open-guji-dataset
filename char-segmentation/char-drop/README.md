# char-segmentation / char-drop —— 字有没有被整个丢掉

## 这个分片在测什么

**单字墨段有没有被 `type == "char"` 的格接住。** 不是「切得深不深」
（那是 truncation），不是「墨在不在网格覆盖的区间里」（那是红线普查），
而是**这个字最后有没有被取出来**。

量法（口径与 `eval_truncation.col_runs` **逐字一致**，尺子分家就一起瞎）：

1. 逐列取原始行墨投影，切出「单字墨段」（高 0.45~1.35 格）；
2. 数该段有多少行被 `type == "char"` 的格覆盖；
3. 覆盖 **< 50%** 判「丢」。

## 为什么必须单独立一把

2026-08-26：`clip_refit` 在整页坐标里找相位，把首线挪到裁窗顶之上，
`bounds[0]` 变负 → `cells_from_bounds` 里 `crop[负:正]` 切出**空数组** →
`_junk_free_ink` 见 `h<6` 返回 0 → **整格判 `empty`，格里的真字消失**。
受害列的新首格墨率 0.34~0.40，满格是墨。

当时在跑的四把尺子**一把都没报**：

| 尺子 | 量的是什么 | 为什么漏 |
|---|---|---|
| truncation | 格线切进字身多深 | 字整个落在一格之内，**一刀没切**，报 0% |
| 红线普查 `_uncov_ink` | 墨在不在网格**覆盖的区间**里 | 墨确实在网格里，只是承载它的那一格被判成空 |
| seam 重切缝 | 格线处的墨量比值 | 少一格 → 少一条缝，分数反而**变好** |
| 正文字格总数 | 全书 24255 → 24251 | 掉 4 个，淹没在正常波动里 |

**「墨在网格内」和「墨被取出来」是两把尺子。**

## 跑分

```bash
cd open-guji-cv
PYTHONPATH=. python scripts/eval_char_drop.py ../open-guji-dataset/char-segmentation
PYTHONPATH=. python scripts/eval_char_drop.py ../open-guji-dataset/char-segmentation --all     # 列全部条目
PYTHONPATH=. python scripts/eval_char_drop.py ../open-guji-dataset/char-segmentation --update  # 重冻
```

**回归口径：零容忍那一类——丢字数只许降不许升。**

同一套判据做进了 `grid_segment.dropped_char_runs`，供 Pass 2a4
（文字带窗口放开择优）当第三条采纳通道用：比例判据（「漏墨率至少减半」）
有硬门槛，`vol02/152` 实测 0.02372 → 0.01246 只差 0.0006 没跨过去，
那一列抬头的两个字就此丢掉。**能直接数的东西不要拿比例去猜。**

## 已知局限

- 「单字段」靠高度窗切出来，**上下粘连**成一坨的浓墨页里切不出段，
  那些页这条尺子看不见（与 truncation 同病）；
- 列尾版框带里的横条/墨疙瘩会被当成单字段，因此基线里有一批**并非真字**
  的条目——它们不影响回归口径（只比数不比内容），但清零之前别把这 17
  当成「17 个字丢了」；
- 覆盖门槛 50% 是几何判据不是语义判据：一个字被两格各盖一半时不算丢
  （那属于 recrop / seam 的管辖）。
