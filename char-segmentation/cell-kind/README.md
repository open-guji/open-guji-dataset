# char-segmentation / cell-kind —— 列内字格的类型

## 这个子集在测什么

`row-boundaries` 测的是"格线切在哪"（纵向 y 坐标），这个子集测的是**格线切
好之后，每一格里是什么**——`open_guji_cv/utils/row_boundaries.py` 的
`Cell.kind`。这是 Step3（单列文字切分）此前完全没有独立人工金标的一层：
夹注判据（迁移自生产 `clustering/extractor.py`）的"准确率"此前只对照过
生产 `phase4_chars` 的存量输出，那不是金标（生产自己也会错），只能验证
"迁移没退步"，回答不了"这一层真实的精确率/召回率是多少"。

## 三选一，不是四选一——一个真实踩过的坑

标注时给的是四选一：`char`(字) / `blank`(空白) / `raised`(抬头) /
`jiazhu`(夹注)。收回 39 格标注后，只有 2 格跟算法输出不一致，都在
`vol01/33 col2`——算法判"抬头"，人判"字"。

查下来**这不是标错，是选项本身把两件事混成了一件事**。标注页给的是
单格裁紧图（只包住这个字的墨迹外接框，见 `open-guji-cv/scripts/
build_kind_gold_candidates.py`），从这张图上**看不出这一格相对版框线
的位置**——是不是"抬头"是一个相对位置判断（这一格的顶边有没有伸到
版框线以上），不是这一格本身"是什么"的判断，塞进同一个四选一让人在
不该有的信息缺失下做判断。

2026-09-01 定案（用户原话：「不需要区分抬头和普通字，它们都是字，按
坐标来区分位置」）：`Cell.kind` 收窄成三选一（`char`/`blank`/`jiazhu`），
抬头改用 `Cell.raised: bool` 这个独立字段表示——由 `y0 < border_top -
raise_tol` 直接算，不经过人工判断，也不影响 `kind`。任何 `kind` 的格都
可能 `raised=True`（比如夹注格理论上也可以是抬头，虽然实践中没见过）。
改完口径后，把标注里的"抬头"折叠回"字"，**39/39 全部一致**，没有重标。

这个教训本身比数字更值得记：**给标注工具设计选项之前，先想清楚"这道题
标注人凭手上这张图能不能真的判断"**——单格裁紧图能回答"这是不是双行
小注"（两个子列的墨迹在这张图里全看得见），回答不了"这个位置正不正常"
（正常与否要跟别的格比，裁紧图恰恰把这种比较信息裁掉了）。

## 抽样

**先测标注流程好不好用**（用户 2026-08-31 定），不是按分层抽样铺开的
正式取样——5 列，覆盖：

| 列 | 内容 | 挑选理由 |
|---|---|---|
| `vol02/27` col5 | 短夹注段（2格） | 贴 `jiazhu_split.MIN_RUN=2` 的下限 |
| `vol02/109` col8 | 典型夹注段（4格） | 常规情况 |
| `vol02/4` col8 | 长夹注段（7格，贴列尾） | 段拉长会不会露馅 |
| `vol02/19` col9 | 段端单字尾 | 已知生产漏检的真实案例（新链路多切出一格，人工核对是对的——见下）|
| `vol01/33` col2 | 抬头 + 句读提前结束的空白尾列 | 顺带覆盖 raised/blank，不止夹注 |

`vol02/19` col9 那一格额外值得记一笔：新链路（`row_boundaries.
segment_column`）比生产 `phase4_chars` 多切出一格——这批人工金标独立
确认了新链路是对的，生产那边漏检（四库提要「浙江巡撫採進本」7 字奇数
小注，生产只切出 5 个字，`撫` 那格漏了）。细节见 open-guji-cv
`.claude/doc/segmentation_v2_pipeline.md` Step3 节。

## 标注方法

`review-artifact` 交互标注页（自存裁决，`open-guji-cv/scripts/
build_kind_gold_candidates.py` + `build_kind_gold_label.py`，均未入库，
生成过程见 open-guji-cv `artifacts/README.md`「Step3 格类型试点金标」条目）。
39 张单格裁紧图卡片，**不显示算法自己的判断**——判断先存进候选文件
（不入库），标注人裁完之后才拿来核对，避免机器判断带偏人工标注。

## 结果

| 类型 | 人标 | 算法 | 一致 |
|---|---|---|---|
| jiazhu | 17 | 17 | 17/17 |
| blank | 12 | 12 | 12/12 |
| char | 10 | 10 | 10/10（含 2 格原判"抬头"、按新口径折算） |

**39/39（100%）**。小注/空白两类满分；`char` 那 2 格的分歧是标注口径
问题（见上），不是识别错误。

## 跑法

```bash
python open-guji-cv/scripts/build_kind_gold_candidates.py   # 未入库，重新截图块
python open-guji-cv/scripts/build_kind_gold_label.py out.html   # 出标注页
```

对照数据在 `samples/*.json`，每个文件一列，`slots` 是该列若干物理格
（`pos` 从上到下连续编号，不是 `Cell.slot`——`slot` 的负数编号是对外展示
口径）的 `kind` 金标；`reproduction` 字段记了这一列的几何是怎么切出来的，
方便核对新算法的输出是不是切在同一批格子上。

## 已知局限

见 `metadata.json` 的 `known_limitations`——样本小、没有负例、不含夹注缝
精确坐标、`raised` 完全没有独立金标（这一批试标已经证明单格裁紧图判断不了，
要标就得换工具：整列缩略图 + 版框线标记，或者带上下文的窗口）。
