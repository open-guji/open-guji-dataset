# char-segmentation / row-boundaries —— 列内字格纵向边界

## 这个子集在测什么

单个列被射影矫正成竖直矩形之后，纵向按刚性网格切成 `chars_per_line`(21)
个格位（含开头的空白格）。这个子集记录的是**每个格位分界线的精确 y 坐标**，
不是"这一格是不是字"这种粗判——是几何量，直接可以拿来算任何切分算法
"切在哪"跟"该切在哪"差多少像素。

## 金标怎么来的

1. 起点：`phase3_char_grid` 产物自己的格线（`grid_strict` 分割器给的
   `y_top`/`y_bottom`），这不是随便定的初值——production 已经用真实投影
   信号切过一遍，比从零猜靠谱。
2. 人工在交互标注页里，对着射影矫正后的列图 + 拖拽把每条线跟投影波谷
   对齐核校，9 列全部逐点核对确认（不是抽查）。
3. 所以金标反映的是"人眼认为该切在哪"，不是"production 认为该切在哪"——
   跟 phase3 原始值的差距本身就是一个有意义的信号（见下）。

## 坐标系（金标为什么不会过期）

`boundaries` 记在**该列射影矫正后的局部坐标系**里，不是原图坐标。样本文件
一并存了矫正所需的全部几何量（`left_line`/`right_line` 的 position+slope，
取整页高，不按上下版框裁）——只要这两条竖线的探测结果不变，任何新算法都
能重新生成同一个矫正矩形，拿这批 y 坐标直接算误差，不需要重新标注。

每列 22 个点 = 21 格的 21+1 条边界（首尾两条贴版框）。

## 当前样本

`vol02/135`（正文中段普通页，`page_type=body`，非卷首非抬头，9 列 21 格）。
只有这一页，**样本量小，只能验证单页内规律，不能当通用基线**。

## 分析 1：格高一致性

```
全部 189 个格高(9列×21格): 均值 108.8px  std 7.0px  CV 6.5%
列间格高均值: 108.0 ~ 109.6px，9列本身几乎等高
```

**九列的格高高度一致**（列间差异极小），列内单个格高的离散（CV 4.4%~8.6%）
主要来自笔画疏密造成的视觉判断误差，不是版式本身不齐。（列8 曾有一处
标注失误——开头一格误标成 59.4px，用户复核后改回 106.7px，跟其他列一致；
上面的数字是修正后的。）

## 分析 2a：金标是不是波谷？

排除贴版框的两条边界点和"空白格/空白格"分界点（那一带本来就没墨，谈不上
波谷）之后，剩下 171 个分割点（9列 × 每列19个）：

```
离局部最低点(±40px窗口内)的距离: 均值 4.7px  中位 2.0px  最大 40.3px
  <=5px 占比 80%   <=10px 占比 92%
墨量在局部窗口里的排位(0=正好在最低点,1=正好在最高点): 均值 0.028 中位 0.012
  <=0.15(几乎就是最低点) 占比 98%
```

**结论：金标点绝大多数就是局部墨量最低点本身**——98%的分割点落在局部
墨量排位后15%以内，中位数只偏离精确最低点2像素。少数偏离较大的点
(最大40px)基本都出现在列5、列7那种"整段连续偏移"的地方（见下）——不是
人眼没找准波谷，是那一段的波谷位置本身跟"整齐等分21份"的预期对不上号，
人工在两者间做了取舍。

## 分析 2b：旧算法/生产产物跟人工金标差多少

| 对照对象 | n点 | 均值误差 | 最大误差 |
|---|---|---|---|
| **生产 phase3(`grid_strict`)产物边界** | 198 (22×9) | 20.4px | 68.0px |
| 算法1：硬分21份+固定padding(0,22) | 180 (20×9) | 36.0px | 102.1px |
| 算法3：核实剔空白后按实际格数(19)等分 | 162 (18×9，仅真实字格区间) | 23.8px | 73.2px |
| **算法6：单列弹性DP（本轮新做，见下）** | 180 (20×9) | **6.6px** | **37.6px** |

phase3 产物这行不是随便找的对照——它就是当前生产用的 `grid_strict` 分割器
真实吐出来的格线（人工标注时拿它当初始值，之后逐点核对/挪动，所以差值
就是"生产算法离人工判断有多远"）。算法1/算法3是本项目上一轮离线试的两种
简单等分策略，都明显不如生产算法，更不如下面新做的弹性DP。

## 分析 3：弹性DP——让20个分割点"间隔接近1/21，同时落进波谷"

**思路**：不再硬性要求间隔恰好等于 `(border_bottom-border_top)/21`，而是
把它当"先验"，用DP在每个点自己的候选窗口里找一条全局最优路径——
每一步的代价 = 该点的墨量(越低越好，鼓励落进波谷) + 该点到"上一个选中点+
预期周期"的偏差的平方(乘以权重λ，越接近预期间隔越好)。这跟直觉里"抬头也
在波谷附近找、但不能跟前一个字离太远也不能太近"是一回事。

```python
def dp_fit(row_proj, dst_w, border_top, border_bottom, lam, slack=0.42, n_slots=21):
    P = (border_bottom - border_top) / n_slots      # 预期周期(先验格高)
    ink = row_proj / dst_w                            # 归一化墨量，[0,1]
    # 前向DP：dp[k][y] = ink[y] + min_{y'} ( dp[k-1][y'] + lam*(((y-y')-P)/P)**2 )
    # y 只在 border_top+k*P 附近 ±slack*P 的窗口里取候选
    # 回溯得到 border_top, y_1, ..., y_20, border_bottom
```

在这页(vol02/135)上网格搜索λ：λ=0（纯找波谷，不管间隔）均值误差9.1px；
λ过大（>2，几乎变回硬等分）又涨回8~9.5px；**λ=0.1 最优，均值误差6.6px、
最大误差均值37.6px**——比生产 `grid_strict` 产物（20.6px / 84.3px）和
两个离线等分算法都明显更接近人工金标。逐列看：

```
列0 6.1/35.6px  列1 4.8/26.4px  列2 4.7/34.6px  列3 4.4/30.4px  列4 8.1/37.9px
列5 9.9/54.0px  列6 4.9/32.1px  列7 8.6/48.3px  列8 8.2/39.3px
```

列5、列7 依然是误差最大的两列——跟分析2里"phase3原始值系统性偏移最大的
就是这两列"是同一批列，说明这两列本身存在DP窗口(±0.42×周期≈45~49px)
也未必兜得住的更大结构性漂移，值得单独细看（比如放宽slack、或换成
跨列联合估计周期）。

### 生产其实已经有同一个想法，但没在这页上生效

`open_guji_cv/clustering/grid_segment.py` 里已经有一个几乎同构的
`dp_boundaries()`（line ~1939，每格 ±15% 弹性 + 全局DP），通过
`elastic_recut()` 接进了生产的 `grid_strict` 主路径——但只在"骑线比例"
(线上墨/格心墨) ≥ 0.45 时才触发，而且首尾线挪动超过 0.30×格高会被
"锚点闸"拒绝、回退到不修正。上面的"phase3产物边界"（也就是我们在这页上
实测的生产真实输出）离人工金标还有20.6px均值/84px最大误差，说明
`elastic_recut` 在这页至少部分列上**要么没触发，要么被锚点闸拦了**——
这是个值得单独排查的线索，但样本只有1页，不足以下结论，建议先扩到多页
再决定要不要动生产阈值。

### 人工调整最大的几处

```
列7 点11   人工1366   phase3原始1298   差68.0px
列7 点10   人工1260.7 phase3原始1193   差67.7px
列7 点12   人工1467.7 phase3原始1401   差66.7px
列7 点8    人工1046.7 phase3原始982    差64.7px
列7 点7    人工932.7  phase3原始869    差63.7px
```

列5、列7 不是单点跳变，而是从中段开始连续 8~9 个点位都朝同一个方向
偏移 53~68px（列7 全部偏大/人工值更靠下，列4 相反、全部偏小）——这跟
`char-ocr`/`char-segmentation` 之前反复处理过的"整列格线相位漂移"
（`grid_shift`，见 open-guji-cv 任务 #14/#40）是同一种形状：单个格高
估计得有点偏差，累积几十格之后就偏出十几到六十几像素。列1、列3几乎
没被动过（均值调整 2.4~3.6px），说明 phase3 在那两列上切得确实准，问题
不是全局性的，是逐列独立发生的。

## 跑分

暂无独立评测脚本（样本量只有1页，先靠这份 README 里手算的基线）。
后续扩到多页后按 `page-geometry` 的方式接一个 `eval_row_boundaries.py`。

本轮"分析3"的弹性DP是离线验证用的简化重实现（公式见上），跟生产
`open_guji_cv/clustering/grid_segment.py::dp_boundaries` 是同一个思路，
尚未提交进 open-guji-cv 代码库，只是拿这1页金标快速试参数用。

## 样本怎么造的

1. `open_guji_cv/utils/peak_line_search.py` 探测该页10条竖线 + 上下边框；
2. 用左右两条竖线做射影矫正，切出9条竖直矩形长条，算行/列投影；
3. 以 `phase3_char_grid` 产物的格线为初始猜测，生成交互标注 artifact；
4. 人工拖拽/键入核校 22×9 个分割点，逐列确认 `reviewed=true`；
5. 读回 artifact 状态，写入 `samples/vol02_135.json`。
