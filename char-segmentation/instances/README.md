# char-segmentation / instances —— 单字图块切分质量

## 测什么

列切成单字之后，图块可能有三类毛病（与人工审查用的标记词一致）：

| 标签 | 含义 |
|---|---|
| `clean` | 正例：就是完整的本字，没有别人的墨 |
| `contaminated` | 混入界行竖线 / 版框 / 上下邻字残余 |
| `truncated` | 本字的墨被切掉了一部分 |
| `not_text` | 根本不是字（版框角、整条横线、空格位）|

## 判定原则：只看墨，不看框

**图块多裁一点空白不算失败**——空白不影响下游归一化与识别。所以：
混入 = 多了别人的墨，截断 = 少了自己的墨，**与外接框大小无关**。

逐像素的细粒度指标（`keep_recall` / `drop_precision`）在合成数据集
[`../cells`](../cells) 上跑——那里能造出逐像素金标，且天然对空白免疫
（两个指标都只统计墨迹像素）。本数据集是**真实图块**，人工给实例级
四分类标签，两者互补而不重复。

## 评的是「自检」，不是「切分」

人工标签描述的是**当前**输出的质量。重跑切分后标签就不再对应，因此它
**不能**当作可自动重跑的切分回归基准。真正能自动化又有用的问题是：

> 管线能不能自己发现坏图块，把它们送进人工审查队列？

所以被测对象是 `CharInstance.flags`，任意 flag 即算「被标记」——驱动
审查的是有没有进队列，不是标了哪个具体原因。

```bash
cd open-guji-cv
python scripts/eval_instance_quality.py ../open-guji-dataset/char-segmentation/instances
```

## 当前基线

```
  clean        (正例) n= 50  被标记   7     14%
  contaminated (缺陷) n= 12  被标记  12    100%
  not_text     (缺陷) n=  5  被标记   5    100%

缺陷检出率 100%   标记精确率 71%   正例误报率 14%
按列型：rigid 缺陷 15 检出 100%（误报 12%）/ elastic 缺陷 2 检出 100%（误报 20%）
```

分两层，因为「能自动处理」和「要人来看」是两种不同的结论：

| 层 | flags | 缺陷召回 | 误报 | 用途 |
|---|---|---|---|---|
| 确定层 | `rule_bar` `edge_blob` `frame_bars` | 71% | **0%** | 成因明确，下游可直接自动处理 |
| 疑似层 | `wide_gap` `boundary_ink` | 94% | 14% | 送人工审查队列 |
| 合计 | | **100%** | 14% | |

### 为什么要按缺陷形状拆开

原先只有一个笼统的 `boundary_ink`（上下边缘带墨量占比），实测
88% 召回 / 10% 误报。它分不开两件事：界行竖线贯穿全高会在边缘带留墨，
**顶天立地的高字同样会**。按形状拆开之后每个判据都对应一种物理成因：

- `rule_bar` —— 细长、近乎满高的**独立**连通体 → 界行/版框竖线混入。
  位置**不限于贴边**：实测混入竖线的 x/W 从 0.08 到 0.96 都有（版心宽度
  与切分相位共同决定），限定「贴边」反而漏掉一半。汉字里没有哪个**独立**
  部件既满格高又这么细——满高的竖笔总是连在字身上。
- `edge_blob` —— 连通体**整体**落在上/下边缘带内 → 邻字残余。是「整体落在
  带内」而不是「有墨落在带内」，后者会把高字一起冤枉。
- `frame_bars` —— 近乎满宽的扁横条 **≥2 条** → 版框横线，整块不是字。
  为什么要数到 2：单条满宽扁横条就是**「一」字本身**——旧的 `rule_like`
  判据（单条即报）把 5 个干净的「一」全判成了线，现已退休。

### 全书实测：约四分之一图块仍带界行竖线

vol01 全书 24883 个图块上跑一遍：

| flag | 命中率 |
|---|---|
| `boundary_ink` | 44.1% |
| `wide_gap` | 25.8%（独立命中 3.3%）|
| `rule_bar` | **23.7%** |
| `edge_blob` | 4.3% |
| `bad_seg` | 1.0% |
| `suspect_empty` | 0.9% |
| `frame_bars` | 0.4% |

`rule_bar` 的 23.7% 目视抽查了 24 例，**全部确为图块里带着界行竖线、
本字完好**。这不是误报率高，是问题本身就这么普遍——列条裁剪留下的
系统性残余，值得单独修掉，而不是只标出来送审查。

## 抽样有意偏置——不要把占比读作缺陷率

67 个样本里 40 个从**历史人工审查标记过的问题位置**抽（那些位置值得
复查），27 个从刚性/弹性列随机抽。所以各类占比**不是全书真实比例**，
只能用于比较不同算法在同一批样本上的表现。

（历史标记只有约 60~67% 能对上当前切分的 `page:col:idx`——弹性列改成
顺序编号、切分本身也改过——所以它们只当抽样线索，金标是对**当前输出**
重新目视标注的。）

## 重标记录（2026-08-22）

`segment` 加入列型分类后重跑切分，**2771 个图块内容发生变化**，落在本表
里的有 15 个：12 个重标、3 个 ID 已不存在（移出）。这正是下面那条
「实例 ID 会随切分失效」的实例，按数据集自己的规矩处理——**不是沿用旧
标签接着测**，那会得到互相矛盾的数字（当时确实先测出了一版
truncated 检出 0% 而离线分析说 100% 的报告，才发现标签过期）。

重标结论：**切分本身变好了**——原来的 2 个 `truncated`、1 个 `not_text`、
3 个 `contaminated` 重看后都已是完整干净的本字；新出现 1 个混入界行竖线、
1 个空位吃进版框线。

代价是本批样本**现已没有 truncated 实例**，截断检测能力在这个数据集上
暂时无从验证。这不代表全书没有截断，只说明这 67 个样本覆盖不到——
需要另行抽样补充，已记进 `metadata.json` 的 `known_limitation`。

## 标注方法

每个图块渲染成左右对照：左 = 原图带图块边界（黄框）与上下文，
右 = 图块内连通体着色。据此判断有没有多出别人的墨、有没有缺自己的墨。
标注表在 `open-guji-cv/scripts/build_instance_dataset.py` 的 `LABELS`。
