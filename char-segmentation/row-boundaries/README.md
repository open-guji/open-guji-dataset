# char-segmentation / row-boundaries —— 列内字格纵向边界

## 这个子集在测什么

单个列被射影矫正成竖直矩形之后，纵向按刚性网格切成 `chars_per_line`(21)
个格位（含开头的空白格）。这个子集记录的是**每个格位分界线的精确 y 坐标**，
不是"这一格是不是字"这种粗判——是几何量，直接可以拿来算任何切分算法
"切在哪"跟"该切在哪"差多少像素。

## 金标怎么来的

1. 起点：`phase3_char_grid` 产物自己的格线（`grid_strict` 分割器给的
   `y_top`/`y_bottom`），这不是随便定的初值——production 已经用真实投影
   信号切过一遍，比从零猜靠谱。
2. 人工在交互标注页里，对着射影矫正后的列图 + 拖拽把每条线跟投影波谷
   对齐核校，9 列全部逐点核对确认（不是抽查）。
3. 所以金标反映的是"人眼认为该切在哪"，不是"production 认为该切在哪"——
   跟 phase3 原始值的差距本身就是一个有意义的信号（见下）。

## 坐标系（金标为什么不会过期）

`boundaries` 记在**该列射影矫正后的局部坐标系**里，不是原图坐标。样本文件
一并存了矫正所需的全部几何量（`left_line`/`right_line` 的 position+slope，
取整页高，不按上下版框裁）——只要这两条竖线的探测结果不变，任何新算法都
能重新生成同一个矫正矩形，拿这批 y 坐标直接算误差，不需要重新标注。

每列 22 个点 = 21 格的 21+1 条边界（首尾两条贴版框）。

## 当前样本

`vol02/135`（正文中段普通页，`page_type=body`，非卷首非抬头，9 列 21 格）。
只有这一页，**样本量小，只能验证单页内规律，不能当通用基线**。

## 分析 1：格高一致性

```
全部 189 个格高(9列×21格): 均值 108.5px  std 7.9px  CV 7.3%
真实字格(跳过每列开头2个空白格, 171个): 均值 108.5px  std 7.0px  CV 6.5%
列间格高均值: 105.3 ~ 109.6px，列间std仅 1.2px(9列本身几乎等高)
```

**九列的格高本身高度一致**（列间差异 CV<1.2%），列内单个格高的离散主要来自
笔画疏密造成的视觉判断误差，不是版式本身不齐。列8 是唯一例外
（CV 12.5%，开头一格量出 59.4px，明显小于其余 ~108px）——见下面"phase3
原始值差距最大的调整"，这一格的分界点被人工大幅挪动过，值得单独确认是
真实版式（这一列头部真的挤了一个短格）还是标注误操作。

## 分析 2：旧算法/旧产物跟人工金标差多少

| 对照对象 | n点 | 均值误差 | 中位误差 | 最大误差 | ≤5px占比 | ≤10px占比 |
|---|---|---|---|---|---|---|
| phase3 产物原始边界* | 198 (22×9) | 20.6px | 15.3px | 84.3px | 28% | 38% |
| 算法1：硬分21份+固定padding(0,22) | 180 (20×9) | 36.0px | 30.2px | 102.1px | 8% | 17% |
| 算法3：核实剔空白后按实际格数(19)等分 | 162 (18×9，仅真实字格区间) | 23.8px | 16.2px | 73.2px | 14% | 32% |

\* phase3 原始边界是标注页的**初始值**，人工是在它上面拖拽调整的，这一行
不是独立算法的盲测结果——它衡量的是"人工总共挪动了多少"，不是"phase3
预测得多准"。真正意义上从零算的两个算法（算法1、算法3）里，**算法3依旧
更接近人工金标**，但两个算法在这页上的误差都明显比之前用 phase3 自己的
格线当金标时算出来的误差大（之前算法3对着 phase3 格线是 6.7px 均值，现在
对着人工金标是 23.8px）——说明 phase3 自己的格线本身跟人工判断也有不小
差距，用它当参照会低估真实误差。

### 人工调整最大的几处

```
列8 点0    人工162.3  phase3原始78.0   差84.3px
列7 点11   人工1366   phase3原始1298   差68.0px
列7 点10   人工1260.7 phase3原始1193   差67.7px
列7 点12   人工1467.7 phase3原始1401   差66.7px
列5 点10   人工1246.7 phase3原始1184   差62.7px
```

列5、列7 不是单点跳变，而是从中段开始连续 8~9 个点位都朝同一个方向
偏移 53~68px（列7 全部偏大/人工值更靠下，列4 相反、全部偏小）——这跟
`char-ocr`/`char-segmentation` 之前反复处理过的"整列格线相位漂移"
（`grid_shift`，见 open-guji-cv 任务 #14/#40）是同一种形状：单个格高
估计得有点偏差，累积几十格之后就偏出十几到六十几像素。列1、列3几乎
没被动过（均值调整 2.4~3.6px），说明 phase3 在那两列上切得确实准，问题
不是全局性的，是逐列独立发生的。

## 跑分

暂无独立评测脚本（样本量只有1页，先靠这份 README 里手算的基线）。
后续扩到多页后按 `page-geometry` 的方式接一个 `eval_row_boundaries.py`。

## 样本怎么造的

1. `open_guji_cv/utils/peak_line_search.py` 探测该页10条竖线 + 上下边框；
2. 用左右两条竖线做射影矫正，切出9条竖直矩形长条，算行/列投影；
3. 以 `phase3_char_grid` 产物的格线为初始猜测，生成交互标注 artifact；
4. 人工拖拽/键入核校 22×9 个分割点，逐列确认 `reviewed=true`；
5. 读回 artifact 状态，写入 `samples/vol02_135.json`。
