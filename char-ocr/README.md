# char-ocr —— 单字识别测试集（G5）

**一句话**：三册 30,265 条 (图块, 参考整理本金标字)，其中 13,405 条把
图块像素冻结进了 `crops/`。格式见 [../doc/char-ocr.md](../doc/char-ocr.md)，
G5 这一步的输入输出契约见 open-guji-cv `.claude/doc/g5_g6_recognition.md`。

| 册 | 内容 | 锚定页 | 实例 | 金标 | 覆盖 | 冻结 |
|---|---|---|---|---|---|---|
| book9 | 《總目》卷首一 10 页 | 9/10 | 1,647 | 1,405 | 85.3% | 1,405 |
| vol01 | 《總目》卷首全册（上諭/職名/目錄/正文混排）| 89/201 | 24,614 | 12,052 | 49.0% | 6,000 |
| vol02 | 《總目》卷一 易類全册（整册皆正文）| 123/186 | 29,790 | 16,808 | 56.4% | 6,000 |

金标来源一律是 `align`——参考整理本逐实例对齐，**取值与任何 OCR 引擎无关**。

## 两份产物

- `expected.json` —— **分层抽样**后的样本，图块像素已冻结。这是测试集。
- `labels_all.jsonl` —— **全部**金标（不含图块），一行一条。给微调用，
  也给全书范围的统计用；它挂在 `instance_id` 上，**会随切分漂移**。

抽样是必要的（4.6 万条逐条存 PNG 要 140MB）。抽样按 页型 × 图块质量 ×
簇大小 × 异体字 分层，稀有层全留、只砍最大的层，各层抽样率记在
`info.json` 的 `sampling_rates` 里。评测脚本据此给出加权聚合。

**抽样分层刻意不含 `align_opcode`。** 它记的是「建集那台管线当时对不
对」，拿它当抽样层再反比加权，加权后的聚合数字会**恒等于**建集管线自己
的转写准确率——一个与被测引擎无关的常数（首版就踩了这个坑：raw 79.90%
/ 加权 89.91%，后者恰好是建集时的转写准确率 88.4%）。它仍是**报告**分层。

### 分层（instance 口径）

| 分层 | n | top1 | top5 | 读法 |
|---|---|---|---|---|
| `page_type:body` | 11640 | 88.60% | 93.78% | 正文，主战场 |
| `flag:clean` | 9690 | 88.82% | 94.17% | |
| `flag:suspect` | 3457 | **89.33%** | 93.84% | **疑似层标记不预示识别失败**，比 clean 还高 |
| `flag:certain_defect` | 258 | **79.84%** | 84.50% | 确定层标记确实伤，低 9pp |
| `cluster:single` | 9776 | 88.83% | 93.91% | |
| `cluster:multi` | 3629 | 88.65% | 93.86% | |
| `common` | 13047 | 89.50% | 94.40% | |
| `variant` | 358 | **62.57%** | 75.70% | **最弱的一层**，低 27pp |
| `opcode:equal` | 11572 | 98.46% | 98.74% | |
| `opcode:replace` | 1833 | 27.66% | 63.34% | 建集时管线错的位置；top5 还能捞回 2/3 |

`flag:suspect ≥ flag:clean` 这一条值得记住：`boundary_ink` 一类疑似层
判据抓的是「边缘带见墨」，而墨足、刻得实的字**本来就更容易认对**。
疑似层只配用来排人工队列，**不能拿来当识别质量的门**。

## instance 与 pipeline 两种口径

G5 在生产里的作用单位是**簇**：只对簇代表跑引擎，结果由全簇共享。

| 口径 | 全体 top1 | `cluster:multi` |
|---|---|---|
| `--unit instance`（逐图块跑引擎）| **88.78%** | **88.65%** |
| `--unit pipeline`（簇内共享后逐实例）| 87.87% | 85.29% |

**簇内共享是净负的**：全体 −0.91pp，落在多元簇里的实例 −3.36pp。

根因用**非循环**的量法确认过（只用金标，不碰任何算法输出）：

```
有 ≥2 条金标的簇 1,107 个，覆盖 2,995 个实例
  纯簇 761/1107 = 68.7%
  即使总是选簇内多数字，仍必错 412/2995 = 13.76%
  折算到全部金标 = 1.36% 的实例因簇污染而注定错
```

而且污染与图块自检**无关**：污染簇里少数派成员的 flag 分布
（clean 85.9%）与多数派（clean 86.5%）几乎一样——不是坏图块混进来了，
是聚类本身把不同的字并到了一起。

## 错误结构

1,504 条 top-1 错误里：

- **12.0% 是纯表面形之差**（為→爲 ×47、説→說 ×19、蓋→葢 ×3…），语义
  已经选对，只是形不对。这类不需要更强的视觉，需要**本版用字证据**——
  归 G6 管，见 context-correction 的消融。
- 头部混淆：`傅→傳×51 日→曰×49 為→爲×47 叉→又×19 人→入×15 郎→即×13`
- top-5 都没捞到的 645 条里，**72.7% 的金标字属于某个异体字组**。
  但在 G5 盲目做异体字扩展是亏的（实测 top5 +0.27pp / top1 −0.36pp）：
  它把概率挪给主形，而 OCR 本来就对的那些字也一起被挪了。

## 已知局限

见 `metadata.json` 的 `known_limitation`。最要紧的：**锚定偏置**（三册
56,051 个实例里只进集 54%，目錄/職名页整理本没收录几乎全落空），
**没有 train 集、跨册与跨书泛化都没测过**，图块随切分陈旧。

## 重建

```bash
cd open-guji-cv
for B in book9 vol01 vol02; do
  PYTHONPATH=. python scripts/build_char_ocr_dataset.py output/$B \
      --corpus corpus/zongmu_wuyingdian_reference.txt \
      --dataset ../open-guji-dataset --shard $B --max-items 6000
done
PYTHONPATH=. python scripts/eval_char_ocr.py ../open-guji-dataset/char-ocr \
    --engines rapidocr --unit instance
```

金标是自动对齐出来的，**重跑脚本即可重建整个集**，不需要重标。
