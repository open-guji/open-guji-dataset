# char-segmentation / column-slots —— 逐列字数人裁

## 这个分片在测什么

**一列到底有几个正文字格**。

| 字段 | 取值 | 问的是 |
|---|---|---|
| `n_slots` | 整数 | 这一列实际的正文格数 |

版式常量（册 yaml 的 `chars_per_line`，如北行日錄刻本 21）是页级先验，
**在个别列不成立**：抬头列可能多一格，卷题页/卷末页可能少几格，版框装不下
时 `effective_body_slots` 会正当下调一格。这些都不是故障，但 DP 要的是
**这一列的**格数——给错了，唯一可行解往往是**丢掉首字**或把两个字挤进一格，
而两者在产物里都不报错。

裁决台在控制台 **Step3 页**（`逐列字数` 面板），事件
`kind=n_body_slots`、`target.step=row_segment`，路由表落到本分片，
同时让该页 Step3 产物显式失效——下次重跑时 `feedback.lookup.resolved_slots()`
读回来覆盖 `effective_body_slots` 算出的格数。

## 为什么需要人裁而不是算

「这一列几个字」**没有可靠的纯信号判据**。实测两条负结果：

- **格高/period 比值判不出来**：北行日錄全书量过「末格高度 >1.3×period」的样本，
  逐个核实全是单字偏高（笔画密或字后带留白），没有一个是真的多字挤压；
  换算法测到的一处真挤压（3 字挤一格）比值反而只有 1.28，比那些假阳性还低。
  **高的不一定挤、挤的不一定高，这把尺子两个方向都不可靠。**
- **墨跨度判据只对「越框」有效**：已知的辅助判据（墨跨度/period）只识别得了
  「抬头字越过版框线」的情形，对「字数超版式常量但没越框」完全不触及。

所以这一类现阶段只能靠人对着图逐格数。裁小图时各留 3px padding——
缩小显示的整列图人眼会漏数或重数，尤其在图片上下拼接处。

## 与 `head-raise-columns` 的分工

那个分片答「这一列是不是抬头、抬高几格」，是**版式语义**；
本分片答「这一列最终切几格」，是**DP 的输入约束**。
抬头列通常（但不总是）比常量多一格——vol01/33 实测四个抬头列里 3 个多一字、
1 个不多，所以两者不能互相推导，各自单独标。

## 锚点

`id` = `<book>:<page>:<col>`，`anchor` 填 book/page/col。
列号从右到左、从 1 开始（与 `column_gate` 产物一致，不是数组下标）。
