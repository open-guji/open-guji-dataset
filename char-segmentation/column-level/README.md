## 这个子集在测什么

| 子集 | 标的是 |
|---|---|

## 三个值得记的发现

### 1. 整列滑格一例都没有

设计这一轮的理由之一是「**整列滑格**是 `row_boundaries_design.md` 记的头号
失败模式，而墨量判据完全看不见它——滑格时每条格线照样落在字缝上、墨量还是
0」。**前半句被实测推翻了**：117 列里 `phase` 一条都没有。后半句因此也无从
验证。这条假设在设计文档里挂了很久，现在至少在这批页上有了直接反证。

### 2. 26 条 partial 里至少 15 条不是 Step3 的错，是列尾被裁

用户裁完直接指出：**有一部分「局部有错」是因为最后一个字被截断了，可能是
Step1 的问题**。查下来属实，而且证据链是闭合的：

- 这 15 条的列图**底边 3 行还压着墨**（`bottom_ink` > 0.05）——末字被列图
  下边界齐齐切掉一截，Step3 拿到的列本身就缺字，怎么切格都不可能对。
- 重灾页 **vol01/138（9 列里 8 列 partial）和 137（3 条）**，这两页的列图
  高度中位数只有 **2377 / 2371px**，比正常页（2415~2493）矮 40~120px。
- 根因在 Step1，而且**早就记在案了**：`border-detection` 的判读记录写着
  「vol01/137、138、141 的下内框磨得极淡……**算法在这三页反而都是错的：
  137/138 咬在末行字的墨上**，141 落在外框粗条上」。咬在末字墨上的下边框，
  正是列尾被裁的直接原因。

所以这 15 条应当记在 **Step1 的账上**。

### 2b. 剩下 11 条逐条查完了：9 条同一个 Step3 缺陷，2 条还是 Step1

| 归因 | 条数 | 列 |
|---|---|---|
| **曲线端点盲区**（Step3，已修）| **7** | 9c3 9c4 32c6 65c2 65c4 142c1 142c2 |
| 端点盲区的**连锁**（Step3，已修）| **2** | 26c2 32c9 |
| **列首被裁**（Step1，对称于列尾）| 2 | 32c4 141c7 |

九条的共同症状是**格线咬在首字或末字的字身上**，根子是两个只在曲线两端
发作、且叠在一起的缺陷：

1. **`_prominence()` 走到端点算不出凸出度**——它往左/右走到「比自己更低的
   点」为止取两侧最高点，走到端点还没遇到更低点时那侧的 max 就停在很低的
   值上。实测这 7 条列的真零墨字缝**距曲线端点只有 0~10px**，凸出度一律
   **0.0**（门槛 16~18），给端点补一堵墙之后是 **61~122**。
2. **`find_valleys` 根本扫不到端点**——循环是 `i = 1; while i < n-1`，判据是
   `curve[i] <= 两侧`。端点只有一侧邻居，判据永远不成立，扫描区间又把它排
   除。vol01/32 c6 的缝就在 `y=0`、142 c1 的在 `y=n-1`，补墙后凸出度 65.8 /
   61.4 都够格，却因为扫不到而落选。

**两条都是「曲线被截断」造成的假象，不是信号**：列图按版框裁出来，列首之上、
列尾之下本来就不存在「更低点」这回事。

那 2 条**连锁**（26c2、32c9）乍看是中间某条格线切错，其实是首点被上面两个
缺陷坑到 40px 之后整列相位后推，到第 3 条格线时真零墨点距前一点只剩 63/75px，
**低于最小间距硬约束 `0.7×period`（80/82px）**，DP 结构上就选不了了。修首点
顺带就修好了它们。

### 2c. 修了，实测

两处各改一点（端点当墙 + 端点单独入选），实测：

| 量法 | 改前 | 改后 |
|---|---|---|
| **117 列 2574 条格线**：切在真零墨 | 80.6% | **83.6%** |
| **117 列**：切进字身（>0.05）| 5.4%（140 条）| **2.8%（72 条）** |
| 那 9 条的最大格线墨 | 0.138~0.206 | 8 条降到 0.008~0.099 |
| `cell-truncation` 应修的格线切在真零墨 | 10/12 | **11/11** |
| `row-boundaries` vol02/135（独立人工金标）| 95 条切进字身 | **95 条，零变化** |
| `row-boundaries` vol01/33 | 10 条 / 均值 0.0287 | 10 条 / 均值 0.0328 |

顺带把 `cell-truncation` 遗留的那条未修缺陷（`vol02_27_col5_b0`）连同它牵连的
`b20` 一起修好了。唯一代价在 vol01/33 的均值墨量（+0.004，切进字身条数不变），
而那页金标本身有循环论证问题（6 列误差精确 0.000），判为小样本波动。

归因 Step1 的 2 条如预期修不好（列图本就缺字），但格线也从 0.170/0.205 降到
了 0.056/0.102。

⚠️ **所以这份 `samples.jsonl` 记的是修复前的状态**：9 条 `endpoint_blindspot`
修好后应当重判为 ok，要「当前算法的列级准确率」得重出卡片、重跑一轮人裁。

### 3. 墨量判据预测不了人裁结果（这是这轮金标存在的理由）

两个自动指标都是**先算好、不上卡**的（避免引导标注人），裁完之后才拿来比：

| 指标 | ok 组 | partial 组 | 能不能当判据 |
|---|---|---|---|
| `max_line_ink` 该列格线落点最高墨量 | 中位 0.0704 | 中位 0.1663 | **不能**——91 条 ok 里有 **55 条**高于 partial 组的最小值 0.0561，重叠得一塌糊涂 |
| `bottom_ink` 列图底边 3 行的墨 | 中位 **0.0000** | 中位 0.1415 | 好得多，但**仍不充分**——全库 39 条 `bottom_ink>0.05` 的列里只有 15 条判 partial（vol01/33、51 底边残墨高却基本判 ok，末字贴着边框但没被切坏）|

`max_line_ink` 正是 `cell-truncation` 那把尺子的列级汇总。它分不开 ok 和
partial，说明**光看「切没切到墨」判不出「这一列对不对」**——这一轮人裁的价值
就在这里。`bottom_ink` 可以当筛查线索去捞「列尾被裁」的页，但别当判据用。

## 数据

`samples.jsonl`，一行一列：

```json
{"id":"col:vol01:138:2","book":"vol01","page":"138","col":2,"verdict":"partial",
 "col_img_h":2374,"bottom_ink":0.1987,"max_line_ink":0.2341,
 "has_warp_gold":false,"stratum":"gate_all","stratum_weight":1.0}
```

`bottom_ink` / `max_line_ink` / `has_warp_gold` 都是**事后**附上去的分析字段，
标注时没给标注人看。`stratum_weight` 恒为 1.0，因为这轮是全覆盖不是抽样。

## 怎么再来一轮

```bash
# open-guji-cv
python scripts/build_step3_column_review.py \
  --manifest output/vol01/step3_input_gate/manifest.json -o out.html
```

卡片 id 冻在 `output/step3_column_review_cards.jsonl`，重出页照旧读就能跟这一轮
对齐。**注意这批裁决会随上游失效**：它挂在「(书,页,列) + 当时那版 Step2 列图 +
当时那版 `segment_column` 输出」这个三元组上，不是挂在坐标上。Step1 的下边框
一修，上面那 15 条列尾被裁的就该变成 ok，得重出卡片重标。这批的长期价值是
**基线数字 + 根因记录**，不是可无限复用的坐标金标。

## 已知局限

见 `metadata.json` 的 `known_limitations`。最要紧的两条：这 13 页正是
`border-detection` 金标那 14 页、当初按**难例**挑的（磨损页、抬头页），
**77.8% 不能直接外推成全书**；以及 **vol02 一列都没有**（Step2 虽已扩页跑了
27 页 vol02，产物没进 git、这一轮够不着）。
